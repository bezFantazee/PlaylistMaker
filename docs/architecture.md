# Архитектура PlaylistMaker

В проекте используется сочетание **Clean Architecture** и **MVVM**. Приложение разделено на Data, Domain и Presentation слои. Для управления зависимостями используется Koin.

## 1. Структура приложения

Основные функциональные области проекта:

- `search` — поиск музыкальных треков через iTunes Search API;
- `player` — предпрослушивание выбранного трека с помощью MediaPlayer;
- `mediaLibrary` — работа с избранными треками, базой данных Room и плейлистами;
- `playlist` — создание, редактирование и просмотр пользовательских плейлистов;
- `history` — хранение истории поисковых запросов;
- `settings` — настройки приложения и управление темой;
- `sharing` — системные действия для отправки приложения и плейлистов, открытия пользовательского соглашения и обращения в поддержку;
- `di` — конфигурация внедрения зависимостей.

## 2. Data Layer

Data Layer отвечает за взаимодействие с внешними и локальными источниками данных.

### Поиск треков

- `TrackApiService` описывает запросы к iTunes Search API.
- `RetrofitNetworkClient` выполняет сетевые запросы.
- `SearchTracksRepositoryImpl` получает результаты поиска и преобразует DTO в доменные модели.

### История поиска

- `PrefsStorageClient` реализует хранение истории через SharedPreferences.
- `TracksHistoryRepositoryImpl` предоставляет операции для работы с историей поиска.

### Медиатека и Room

Для локального хранения данных используется база данных Room — `TrackDatabase`.

В базе предусмотрены сущности:

- `TrackEntity` — информация о музыкальном треке;
- `FeaturedTrackEntity` — данные об избранных треках;
- `PlaylistEntity` — информация о пользовательских плейлистах;
- `PlaylistTrackEntity` — связь треков с плейлистами.

Для доступа к данным используются DAO:

- `TrackDao`;
- `FeaturedTrackDao`;
- `PlaylistDao`;
- `PlaylistTrackDao`.

Репозитории обеспечивают взаимодействие с DAO и преобразование сущностей базы данных в доменные модели. Для наблюдения за изменениями данных используются Flow.

### Воспроизведение

- `MediaPlayerAudioPlayerClient` инкапсулирует взаимодействие с Android MediaPlayer.
- `PlayerRepositoryImpl` предоставляет доменному слою операции подготовки и управления воспроизведением, а также получения текущей позиции.

### Обложки плейлистов

Для хранения изображений обложек используется файловое хранилище приложения.

`FileInternalStorage` сохраняет изображения в app-specific каталоге изображений, полученном через `getExternalFilesDir(Environment.DIRECTORY_PICTURES)`. Путь к изображению сохраняется вместе с данными плейлиста.

Важно: это хранилище используется для обложек плейлистов. Загрузка аудиофайлов для офлайн-воспроизведения в текущей версии не реализована.

## 3. Domain Layer

Domain Layer содержит бизнес-логику приложения и не зависит от конкретных способов получения данных или отображения интерфейса.

В слое используются:

- доменные модели;
- интерфейсы репозиториев;
- интеракторы (Interactors);
- сценарии использования (Use Cases).

Основные сценарии:

- поиск музыкальных треков;
- работа с историей поиска;
- управление воспроизведением выбранного трека;
- добавление и удаление треков из избранного;
- создание, редактирование и удаление плейлистов;
- добавление треков в плейлисты и удаление их из плейлистов;
- получение данных медиатеки;
- управление настройками темы;
- подготовка данных для системного обмена и внешней навигации.

## 4. Presentation Layer

Presentation Layer отвечает за отображение данных и обработку пользовательских действий.

Основные компоненты:

- `RootActivity` — корневая Activity и настройка навигации;
- `Fragment` — экраны поиска, плеера, медиатеки, плейлистов и настроек;
- `ViewModel` — обработка действий пользователя и подготовка данных для интерфейса;
- `LiveData` — передача состояния от ViewModel к UI;
- UI state-модели — представление состояний экранов;
- адаптеры RecyclerView — отображение списков треков и плейлистов.

Для перехода между основными разделами используется BottomNavigationView.

В медиатеке избранные треки и пользовательские плейлисты представлены отдельными вкладками с использованием ViewPager2 и TabLayout.

## 5. Внедрение зависимостей

Для Dependency Injection используется **Koin**.

Конфигурация зависимостей разделена по функциональным областям приложения: поиск, плеер, медиатека, плейлисты, история поиска, настройки и sharing.

Такой подход позволяет централизованно управлять созданием репозиториев, интеракторов, DAO, сетевых компонентов и ViewModel.

## 8. Использованные архитектурные подходы и паттерны

### Repository Pattern

Репозитории скрывают детали получения и хранения данных от остальных слоёв приложения.

### Dependency Injection

Koin используется для предоставления зависимостей и управления их созданием.

### Observer Pattern

LiveData и Flow позволяют наблюдать за изменениями состояния и данных, обновляя интерфейс при их поступлении.

### Strategy Pattern

Используется при организации переключения темы приложения: поведение оформления выбирается в зависимости от пользовательской настройки.

### Debounce

Применяется для ограничения частоты обработки событий. В текущем описании проекта указаны интервалы:

- поисковый ввод — 2000 мс;
- пользовательские клики — 1000 мс.

## 7. Основные сценарии работы

### Поиск музыкального трека

1. Пользователь вводит поисковый запрос.
2. Debounce ограничивает частоту отправки запросов.
3. Presentation Layer передаёт запрос в сценарий поиска.
4. Репозиторий выполняет запрос к iTunes API через Retrofit.
5. Полученный ответ преобразуется из DTO в доменную модель Track.
6. ViewModel обновляет состояние интерфейса.
7. Пользователь видит результаты поиска.

### Добавление трека в избранное

1. Пользователь нажимает кнопку добавления трека в избранное.
2. ViewModel обращается к соответствующему интерактору.
3. Репозиторий сохраняет или удаляет запись через FeaturedTrackDao.
4. Room обновляет данные.
5. Flow передаёт актуальное состояние в слой представления.
6. Интерфейс отображает обновлённый список избранного.

### Работа с пользовательскими плейлистами

1. Пользователь создаёт или редактирует плейлист.
2. ViewModel передаёт данные в соответствующий интерактор.
3. Репозиторий сохраняет информацию о плейлисте через PlaylistDao.
4. При наличии обложки изображение сохраняется через файловое хранилище.
5. Добавление и удаление треков выполняется через PlaylistTrackDao.
6. Актуальные данные плейлиста отображаются в интерфейсе.

### Воспроизведение трека

1. Пользователь выбирает трек.
2. ViewModel передаёт previewUrl в PlayerInteractor.
3. PlayerRepositoryImpl обращается к MediaPlayerAudioPlayerClient.
4. MediaPlayer подготавливает аудиофрагмент.
5. После подготовки пользователь может управлять воспроизведением.
6. ViewModel обновляет состояние плеера и позицию воспроизведения.

## 8. Текущие ограничения реализации плеера

В текущей версии приложение воспроизводит отдельный аудиофрагмент выбранного трека через MediaPlayer.

Пока не реализованы:

- фоновое воспроизведение через отдельный Service;
- системное media-уведомление с управлением воспроизведением;
- очередь треков и автоматическое переключение между ними;
- загрузка аудиофайлов для офлайн-прослушивания.

Эти задачи включены в [планы дальнейшего развития](roadmap.md).
